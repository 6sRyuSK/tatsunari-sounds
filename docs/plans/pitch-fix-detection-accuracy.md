  P0（実声評価セット）・P2'・P3–P5・§4.4 後回し項目は未着手。

## 0. 結論（先に要約）

Codex の指摘は **方向としては妥当だが、原因の特定を誤っている**。実測すると、
検出誤りの主要因は「単一フレーム候補選択」でも「レイテンシの使い残し」でもなく、

> **解析窓長が Min Pitch パラメータの周期数で決まっており、実際に追跡している
> ピッチの周期数になっていないこと**

だった。この 1 点だけで、220 Hz・ビブラート ±100 cent のボーカルに対して
**voiced フレームの 42.4% が 50 cent 以上外れる**（多くは 3 倍音への harmonic error）。
しかも誤り率は **Buffer モードを上げるほど単調に悪化**する（Realtime 9.9% →
Quality 42.4%）。つまり現状、**「Quality」は最も検出精度が悪いモード**である。

Codex が最優先に推す Viterbi trajectory tracker は、この欠陥を直さないまま
その上に載せる形になる。**順序を入れ替えるべき**というのが本書の主張である。

| | Codex の主張 | 実測による評価 |
|---|---|---|
| 1 | 長いレイテンシを精度に使えていない | **△ 半分正しい**。ただし本質は「使い残し」ではなく、レイテンシを増やすと**窓が伸びて精度が下がる**という逆相関（§2.1, §2.2） |
| 2 | 単一フレーム検出→軌跡推定へ移るべき | **△ 前提が誤り**。弱い基音（H1 −30 dB）でも octave error は **0.0%**。単一フレーム選択自体は健全で、誤りは窓長が引き起こしている（§2.1） |
| 3 | 検出・ノート判定・補正カーブを分離すべき | **◯ 妥当**（設計論として。ただし現状の実害は未測定、§2.5） |
| 4 | Preview / Analyze の 2 層化 | **◯ 妥当だが後回し**。固定 lookahead のままでも §3 の P1/P2 で大半が取れる |
| 5 | Tolerance の意味を分離すべき | **◯ 正しい。実測で確認**（Tolerance 12 ct・Amount 100% で残差ちょうど 12.02 ct、§2.4）→ **`Stability` + `Accuracy` へ分割することで裁定済み**（§4.1） |
| 6 | Resynthesis はレイテンシ増では直らない | **◯ 正しい**。加えて PSOLA には別の時間軸ずれがある（§2.2） |

## 1. 実測の方法

`PfCore` の framing（窓長・hop・median 深さ・解析用 HP）を厳密に再現した probe で、
**合成音声の生成 f0 を ground truth**（実装から導かない独立オラクル）として
フレーム単位の誤り率を測った。合成音声は 3 フォルマント（700/1220/2600 Hz）＋
`h^-0.7` の音源ロールオフ＋ビブラート 5.5 Hz ＋ジッタ、breathiness は
**実測 HNR** で較正した。

> **注意（オラクルの限界）**: この合成音声はフォルマントが固定なので、f0 が
> 330 Hz 付近だと H1 が H2 より 20 dB 低くなるという非現実的な状態が起きる。
> その領域の絶対値は生成器のアーティファクトなので、本書では **同一 f0 における
> 条件間の相対比較のみ**を主張に使う。絶対誤り率を実声の指標として扱ってはいけない
> （だからこそ §3 の P0 は実ボーカル評価セットである）。

## 2. 実測で判明した欠陥

### 2.1 【本命 P1】解析窓が「追跡中のピッチ」ではなく Min Pitch で決まっている

`PfCore::applySnapshot`:

```cpp
winLen = std::min ((int) std::lround (kWindowPeriods[mode] * fs / minHz), maxWin);
```

窓長は **Min Pitch の周期数**で決まる。Min Pitch 75 Hz（既定）・48 kHz では
`{1280, 1536, 1792, 2048}` サンプル。これは 220 Hz で歌う歌手にとっては
**5.9 / 7.0 / 8.2 / 9.4 周期**にあたる。

**機構**: 窓が長いほど、窓の中でビブラートによる周期変動が積み上がる。NSDF の
劣化は**ラグが長いほど大きい**ため、真の周期（長ラグ）のピークが劣化し、
サブマルチプルのラグ（短ラグ＝高い周波数）のピークが相対的に生き残る。MPM は
「グローバル最大の 90% に達した**最初の**候補」＝最短ラグを採るので、
**系統的に harmonic error（高すぎる側）へ倒れる**。

同一信号・窓長だけを変えた直接確認（220 Hz, ビブラート ±120 ct）:

| 窓長 | 検出/真値の比 | clarity |
|---|---|---|
| 2048 smp（＝3.2 周期 of 75 Hz、現行 Quality） | **2.94 – 3.04**（3 倍音へ） | 0.81 – 0.86 |
| 655 smp（＝3 周期 of 220 Hz） | **1.000**（全フレーム） | 0.98 – 1.00 |

誤り率（voiced フレームのうち真値から 50 ct 超、Quality、Min Pitch 75 Hz）:

| 歌手 | ±0 | ±50 | ±80 | ±100 | ±150 ct |
|---|---|---|---|---|---|
| 110 Hz（男性, 窓=4.7 周期） | 0.0% | 0.0% | 0.4% | 0.0% | 0.0% |
| 220 Hz（女性, 窓=9.4 周期） | 0.0% | 0.0% | **35.2%** | **42.4%** | **50.7%** |

Min Pitch を上げて窓を短くすると消える（220 Hz・±100 ct）:

| Min Pitch | 75 | 100 | 130 | 160 | 200 Hz |
|---|---|---|---|---|---|
| 窓/周期 | 9.4 | 7.0 | 5.4 | 4.4 | 3.5 |
| 誤り率 | 42.4% | 26.2% | 0.5% | **0.0%** | **0.0%** |

**Buffer モードとの逆相関**（220 Hz・±100 ct・Min Pitch 75）:

| mode | 窓 (min-pitch 周期) | 窓 (歌手の周期) | 誤り率 |
|---|---|---|---|
| 0 Realtime | 2.0 | 5.9 | 9.9% |
| 1 Fast | 2.4 | 7.0 | 25.5% |
| 2 Normal | 2.8 | 8.2 | 34.9% |
| 3 Quality | 3.2 | 9.4 | **42.4%** |

サンプルレート非依存（44.1 / 48 / 88.2 / 96 / 176.4 / 192 kHz で 42.4–42.9%）＝
**構造的欠陥**であってレート依存のチューニング漏れではない。

なお「弱い基音では単一フレーム選択が破綻する」という Codex の前提は**成立しない**:
H1 を −18 dB / −30 dB 減衰させても octave error は **0.0%**（`core/tests/
pitch_detector_test.cpp` の missing-fundamental テストとも整合）。**壊しているのは
窓長であって候補選択ではない。**

#### 検証済みの対策と、**否定された**対策

- **有効（検証済み）**: 窓長を「**前 hop で確定した f0** の 4 周期」にする
  （unvoiced / コールドスタート時のみ現行の長い窓）。
  220 Hz ±100 ct で **42.4% → 2.9%**、全 Buffer モードで **9.9/25.5/34.9/42.4%
  → 3.0/3.0/2.9/2.9%**、全レートで 2.8–2.9%。80/90/110 Hz の低域取得は
  **0.0% / voiced 100% を維持**（＝窓を Min Pitch で決めていた本来の目的を壊さない）。
  レイテンシ増は **ゼロ**。
- **無効（実測で否定）**: 同一 hop 内での 2 段推定（粗推定→その f0 で窓を張り直す）。
  段 1 が既に 3 倍音を返しているので段 2 はそれを追認するだけで
  **42.4% → 42.4%** と全く効かない。**「前 hop の f0」＝時間方向のフィードバック
  であることが本質**。
- **無効（実測で否定・有害）**: 素朴な sub-multiple sieve（採用ラグ τ に対し 2τ,
  3τ の NSDF が近ければ低い方を採る）。**周期 P の信号は 2P でも必ず周期的**なので
  NSDF は判別力を持たず、クリーンな信号で **誤り率 100%**（正しい f0 を
  サブハーモニクスへ引きずり下ろす）。Codex の言う "harmonic support" による候補
  スコアリングは、この落とし穴を避ける設計（スペクトル包絡の証拠、または
  時間方向の連続性）が必須。
- **不安定（推奨しない）**: 前 f0 の周りに探索帯域を絞る方式は、一度誤ると
  そこにロックインし、レート間で挙動が割れる（44.1 kHz 57.7% vs 96 kHz 23.0%）。

### 2.2 【P2】補正が「それを測った音」より前の音に当たっている（時間軸ずれ）

`runHop()` の解析窓は `written`（＝最新入力）で終わる一方、その瞬間に PSOLA が
合成しているグレインの読み出し位置は `synthMark - lookahead ≒ written - L` である。
さらに **PSOLA の出力ピッチは `ratio × 検出 f0`** で決まる（グレイン間隔 = P/ratio）
——つまり出力ピッチは**実際に読んでいる音の局所ピッチではなく、検出器のタイムライン
に完全に従属する**。probe で `0.5 × detCents` に一致することを確認した。

結果、**出力の音程遷移は入力の遷移より早く起きる**。入力を 45 ct シャープ →
45 ct フラットへ階段状に変えて、出力側の遷移点を入力タイムラインへ写像した実測:

| mode | L | 先行量 (48 kHz) | 先行量 (96 kHz) |
|---|---|---|---|
| 0 Realtime | 1504 | 3.1 ms | 5.3 ms |
| 1 Fast | 1760 | 1.2 ms | −1.0 ms |
| 2 Normal | 2240 | 7.5 ms | 8.4 ms |
| 3 Quality | 3200 | **24.3 ms** | **25.1 ms** |

ここでも **Quality が最悪**（L が窓長より速く伸びるため）。レート非依存＝構造的。

**対策**: 解析窓を `written` 終端ではなく、**グレイン読み出し位置 `written - L` を
中心に**張る（窓は `[written - L - W/2, written - L + W/2]`）。全モードで
`W/2 < L`（最大 1.6 周期 vs 2.35 周期）なので **追加レイテンシはゼロ**、
必要なのは `detRing` を `maxLook + maxWin` に広げる `prepare()` の変更だけ。
これは Codex の言う「未来側を含む中央配置の解析窓」を、Viterbi なしで、
**いま持っている lookahead だけで**実現する。副次効果として、PSOLA に渡す周期が
実際に切っている音の周期と一致するのでグレイン整列も改善するはずである
（後者は要検証）。

### 2.3 【P2】voicing 判定が閾値の崖になっている

Detect Threshold（既定 80%）を境に、**なだらかに劣化せず一気に落ちる**。
実測 HNR を振ったときの voiced フレーム率（Quality）:

| HNR | 30 | 25 | 20 | 15 | 12 | 10 | 8 | 5 dB |
|---|---|---|---|---|---|---|---|---|
| 男性 110 Hz @ thr 80% | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | **0.5** |
| 女性 220 Hz @ thr 80% | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | 94.3 | **7.1** |
| 男性 110 Hz @ thr 50% | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | 99.6 | **99.6** |

つまり 8 dB HNR 付近までは既定で問題なく、そこを割ると**ほぼ全滅**する。
閾値を下げれば 5 dB でも 99.6% 取れるので、**アルゴリズムの限界ではなく判定の
作り方の問題**。対策は voiced 状態のヒステリシス（一度 voiced になったら
低い閾値で維持する）で、Codex の言う "voicing transition penalty" の最小実装に
あたる。実声のブレス区間で誤 voiced が増えないかは P0 の素材で要確認。

### 2.4 【裁定済み → §4.1】Tolerance の意味

Codex の指摘どおり。実測（Amount 100%、定常入力、Normal）:

| 入力 | Tolerance | 出力の目標からのずれ |
|---|---|---|
| +30 ct | 0 ct | **+0.01 ct** |
| +30 ct | 12 ct | **+12.02 ct** |
| −30 ct | 12 ct | **−12.01 ct** |
| +70 ct | 12 ct | **−12.02 ct** |

Amount 100% でも Tolerance のぶんだけ必ず残る。ただし:

- **これは実装のバグではなく仕様**である（`Hard Tune` プリセットは
  `tolerance = 0` で、実測でも ±0.03 ct に着地する）。
- 「12 ct 以内の揺れに反応しない」と「必ず 12 ct 残す」を別パラメータに分けるのは
  **音作りの仕様変更**であり、CLAUDE.md の「Ask a human — 1. Sonic / taste」に
  該当する。→ **`Stability`（反応しない幅）+ `Accuracy`（最終残差）へ分割**する
  ことで裁定済み。確定した既定値・プリセット・migration は §4.1。

### 2.5 検証したが「問題なし」だったもの（誤検知の除外）

- **半音境界の安定性**: 既定 Hysteresis 18 ct では +50.0 ct（境界ちょうど）でも
  ターゲットが振動せず、出力は ±0.03 ct で着地する。Hysteresis 0 のときだけ
  振動するが、それはそのパラメータを無効化した場合の当然の帰結であり欠陥ではない。
- **補正の着地精度そのもの**: ターゲットが安定していれば **±0.03 ct** で着地する。
  Codex の 4「補正後の音程を目標へ正確に着地させる」は、**Tolerance を除けば
  既に達成されている**。
- **弱い基音 / missing fundamental**: H1 −30 dB でも octave error 0.0%。
- **既存のテストスイート**: `pitch_fix_dsp_test` は 48 kHz で全 18 項目 PASS。
  つまり **上記の欠陥はいずれも現行ゲートをすり抜けている**（§3 P0 の理由）。

### 2.6 試作で判明したこと（実装は破棄済み。仕様確定のための計測）

P1/P2/Stability+Accuracy を一度試作して計測し、**仕様を確定させたうえで破棄**した。
得られた事実は次の 3 つで、いずれも §3 の確定仕様に反映してある。

#### (1) 適応窓は単体では **acquisition lock-in** を起こす（P1 の設計を変えた事実）

`PitchDetector` の探索下限は窓長の半分（`lagMax = n/2`）なので、**窓を縮めると
探索できる最低周波数が上がる**。「追跡中 F0 の 4 周期」で縮めると:

- 起動直後の窓は無音→発音の立ち上がりをまたぐため推定がぶれる
- そこで 3 倍音（659 Hz）を掴むと窓が 291 サンプルになり、探索下限が **331 Hz** へ上昇
- **220 Hz が探索範囲外になり、二度と復帰できない**

実測: 220 Hz 定常音（ビブラート無し）で **全 Buffer モード 100% 誤り**
（変更前は 0.0%）。§2.1 で「variant C（帯域を絞る）は危険」と書いたロックインと
同じ失敗が、窓長側から入ってくる。**4 周期は `lagMax` がちょうど 1 オクターブ下の
境界にあたるため安全余裕がゼロ**だった。→ 確定仕様は 6 周期下限 + 定期再取得（§3 P1）。

#### (2) 中央配置は「窓を寄せるだけ」では 0 ms にならない

窓をグレイン読み出し位置へ寄せた結果、**+24.3 ms 先行 → −16.8 ms 遅れ**（Quality,
48 kHz）へ振れた。Normal −19.7 ms、Fast −12.5 ms、Realtime −6.4 ms。
median の群遅延（`(medLen-1)/2 × hopLen` ≒ 10 ms）だけでは **17〜22 ms を説明できず**、
残りの内訳は未特定。→ 確定仕様は「先に内訳を段別に切り分ける」（§3 P2）。

#### (3) Stability / Accuracy の DSP は仕様どおり動くことを確認済み

境界での不連続（デッドゾーンの縁で補正が `Stability - Accuracy` だけ跳ぶ）を避ける
ため、**連続な定式化**を使う:

```
x    = max(0, |err| - Stability)     // デッドゾーンの外側にどれだけ出たか
R    = max(0, Stability - Accuracy)  // Accuracy が余分に要求する距離
d    = x + min(x, R)                 // 縁で 0、x >= R で |err| - Accuracy
dead = sign(err) * d
```

`Accuracy == Stability` で `R == 0` となり **従来の式と完全に一致**、
`Accuracy == 0` で目標に着地する。実測（Amount 100%、定常音）:

| 入力 | Stability | Accuracy | 出力の目標からのずれ | 期待 |
|---|---|---|---|---|
| +30 ct | 12 | 0 | **−0.01 ct** | 目標に着地 |
| +30 ct | 12 | 12 | **+12.00 ct** | 従来どおり |
| +30 ct | 12 | 6 | **+5.96 ct** | 6 ct 残留 |
| −30 ct | 12 | 0 | **+0.01 ct** | 目標に着地 |
| +5 ct | 12 | 0 | **+4.95 ct** | デッドゾーン内は無干渉 |
| +20 ct | 35 | 0 | **+19.98 ct** | デッドゾーン内は無干渉 |

## 3. 推奨する作業順序

Codex の P0→P5 とは **P1/P2 の中身が入れ替わる**。理由は §2.1: 窓長を直さないまま
tracker を載せると、tracker は「系統的に 3 倍音へ倒れた候補列」を滑らかにつなぐ
だけになる。

### P0 — 評価セットとフレーム単位の指標（Codex と同じ、最優先）

Codex の P0 に同意。ただし本書の実測で **合成音声オラクルの限界**（§1 の注意）が
はっきりしたので、優先度はさらに上がる。必要なもの:

- 実ボーカル素材（男女、モーダル/ブレシー/フライ、ビブラート幅の広狭、レガート）
- 手修正した f0 軌跡、voiced/unvoiced 区間、ノート境界、意図的な scoop/fall
- 指標: Gross Pitch Error / Voicing Decision Error / Raw Pitch Accuracy /
  octave（harmonic）error 回数 / ノート境界の時間誤差 / 補正後の目標からの cents 誤差

**リポジトリ規約との関係**: 評価セットとその閾値は「test infrastructure, tolerances,
oracles」に触れるので、CTest ゲートに昇格させる時点で人間の承認が要る
（CLAUDE.md「Ask a human — 2」）。まずは**ゲート化しない計測ツール**として置き、
数字が出てから昇格を相談するのが安全。

### P1 — acquisition と tracking を分離する（**確定仕様**）

§2.6(1) のロックインを構造的に不可能にするため、**「窓を縮める」のではなく
「acquisition モードと tracking モードを分ける」**設計とする。

1. **起動直後は acquisition 窓**（現行の Min Pitch ベースの長い窓）を使う。
2. **median と clarity が複数 hop 安定するまで tracking 窓へ縮めない。**
3. **tracking 窓は追跡中 F0 の最低 6 周期**を確保する。
   → `lagMax = n/2` が 3 周期ぶんになり、**追跡中 F0 の 1 オクターブ下まで探索可能**。
   4 周期はちょうど `lagMax` = 2 周期 = 1 オクターブの境界で安全余裕がゼロ、というのが
   §2.6(1) の実測。6 周期なら 659 Hz に仮ロックしても 220 Hz が探索範囲に残る。
4. **tracking 中も 50 ms 前後ごとに acquisition 窓で全域探索**する。
5. acquisition 側が tracking 側と異なっても **1 回では切り替えず、2〜3 回連続で
   同じ候補が得られたら再取得**する。
6. **unvoiced 継続 / clarity 低下 / 大きな pitch jump では acquisition へ戻す。**

`(c)`（median が安定するまで縮めない）だけでは、**誤った 3 倍音が複数 hop 安定した
場合にそのまま tracking へ入ってしまう**ので不十分。6 周期下限で探索範囲を確保し、
さらに定期的な全域再取得で**ロックインから必ず回復できる構造**にする。

- **段階分割を許す条件**: CPU 負荷や実装量が問題になる場合、今回の P1 は
  `(c) + 6 周期下限`（上記 1・2・3・6）までとし、**定期 acquisition（4・5）は直後の
  必須フォローアップ**に分けてよい。ただし **広域再取得なしを最終仕様にはしない**。
- 効果の目安（4 周期・ロックイン対策なしでの測定値）: 220 Hz ±100 ct で
  42.4% → 2.9%、全モード・全レートで 3% 前後、低域取得は無劣化、**レイテンシ増ゼロ**。
  6 周期での再測定は実装時に行う。

### P2 — 解析位置をグレイン読み出し位置に合わせる（**確定仕様**）

**仕様の定義**: 原音時刻 `t` の pitch estimate を、**同じ原音時刻 `t` を読む grain へ
適用する**。

- **狙いは 0 ms。意図的な先行は入れない。**
- 着手前に §2.6(2) の **17〜22 ms の内訳を段別に特定**する。最低限、次の各段を個別に
  ログしてどこで遅延が加わるかを切り分ける:
  1. 解析窓中心
  2. hop dispatch 位置
  3. median で選ばれた値の時刻
  4. detector 前段 HP
  5. target 変更
  6. retune / glide
  7. `setRatio`
  8. 新 ratio を最初に使った grain
  9. 出力側の測定窓
- **合格基準**: 平均 bias が 0 ms 付近、個々の遷移が **±1 hop 以内**。
- 「わずかな先行」が音楽的に必要になった場合でも、**解析位置の誤差として埋め込まず、
  後から独立した anticipation 仕様として追加**する。

### P2' — voicing ヒステリシス（§2.3）

- voiced 維持用の低い閾値を持たせる。P0 の実素材でブレスの誤 voiced を確認してから。

### P3 — 複数候補 + 時間方向の軌跡最適化（Codex の P1/P2）

**P1/P2 の後**に、残差（§2.1 の ±150 ct 級の広いビブラート、レガート遷移、fry）
に対して実施。ここで初めて Codex の設計が正しく効く。ただし §2.1 の否定結果より:

- 候補スコアに単純な "harmonic support" を入れてはいけない（周期性は整数倍で
  必ず成立するため判別力がない）。**時間方向の連続性とオクターブ跳躍ペナルティが本体**。
- 300 ms 程度の lookahead から始める案（Codex）は妥当。ただし
  **現行の固定レイテンシ内で P1/P2 を先に取り切ったうえで**、追加レイテンシに
  見合う改善が P0 の指標で出ることを確認してから。

### P4 — 検出 / ノート区間 / 補正カーブの分離（Codex の 3, P3, P4）

設計論として妥当。P1–P3 で f0 軌跡が安定してから着手する方が、
どの段が不正確かを切り分けられる。

### P5 — Resynthesis の比較（Codex の 6, P5）

Codex の順序に同意。**同一の確定 ratio curve** を入力として
現行 WSOLA-style / epoch-synchronous PSOLA / phase-locked STFT を比較する。
P2 を先に入れておくと、PSOLA に渡す周期が実際に切る音と一致するので、
比較の土台が正しくなる。

## 4. 決定事項（確定済み — 実装時はこれに従う）

§0 の時点で「Ask a human」に挙げた項目は**すべて裁定済み**。

### 4.1 Stability / Accuracy（旧 Tolerance の分割）

製品方針は「**簡単で高精度な補正**」。したがって既定動作は
**Stability の内側は無干渉／補正を始めたら目標へ正確に着地**とする。

| | 値 |
|---|---|
| 新規インスタンスの既定 | **Stability = 12 ct、Accuracy = 0 ct** |

- **Parameter ID**: `tolerance` を**維持**し、**表示名だけ `Stability` へ変更**する。
  互換を壊してまで `stability` へ改名しない。内部変数名は `stabilityCt` へ変えてよい。
- **Accuracy は新規 ID `accuracy`** をテーブル**末尾**に追加（`add-param` スキルの
  「追加はテーブル末尾」に従う）。純粋な追加なので **minor bump**。
- **既存 6 プリセットは `Accuracy = 旧 Tolerance` を明示設定**して従来の character を
  維持する。全部 0 ct にすると Tolerance の大きい Natural / Gentle 系の音が大きく
  変わるため。プリセットの再設計は**実声で AB 評価できるようになってから別途**行う。

  | プリセット | 旧 Tolerance → 設定する Accuracy |
  |---|---|
  | Natural Vocal | 25 |
  | Tight Pop | 5 |
  | Hard Tune | 0 |
  | Gentle Touch | 35 |
  | Ballad Glide | 18 |
  | Vibrato Keeper | 45 |

- **state migration**: 旧形式の保存済み state に `accuracy` が無い場合は
  **`accuracy = 保存されている tolerance`** として読み込み、既存セッションの音を
  維持する（Policy の `migrateState(StateModel&)` が実装点）。
  **Accuracy 0 ct は新規インスタンスにのみ適用**する。
- DSP の式は §2.6(3) の連続版を使う（境界の跳びとチャタリングを避けるため）。

### 4.2 P1 / P2 の設計

§3 の P1・P2 に**確定仕様として記載済み**（acquisition/tracking 分離＋6 周期下限＋
定期再取得、P2 は狙い 0 ms・内訳の切り分けが先）。

### 4.3 追加レイテンシ

P3 で**追加レイテンシを許容してよい**。ただし具体的な量、および Buffer モードとして
出すか独立した Analyze モードにするかは**後回し**（§4.4）。

### 4.4 後回しでよい項目

- P2' voicing ヒステリシス（実声素材待ち）
- P3 の追加レイテンシ量
- Buffer モードか Analyze モードかの UI 判断
- 評価セットの CTest 昇格
- 評価閾値の最終決定

### 4.5 実声素材

P0 の評価セットは**ユーザーが後日アップロードする**。それまで P0 は保留。
**P1 / P2 / 4.1 は素材なしで進められる**（合成音オラクル＋構造不変量で足りる）。

## 4bis. P1 と同時に入れる contract test（必須）

`kWindowPeriods` の意味変更に伴い、最低限これらを今回の回帰テストへ入れる。
オラクルは**合成時の f0**（実装から導かない）、`write-dsp-test` スキルの規約に従う。

1. **220 Hz が起動時に第 3 倍音へ永久ロックしない**
2. **659 Hz へ仮ロックしても 220 Hz へ回復できる**
3. **tracking 窓が最低 6 周期を確保する**
4. **acquisition が所定の間隔で実行される**
5. **acquisition 結果 1 回だけでは track を切り替えない**
6. **複数回一致すれば再取得する**
7. **本当のオクターブ跳躍は誤って元へ戻さない**
8. **全サンプルレートとブロックサイズで挙動が維持される**

3–6 は内部状態の観測が要るので、`PfCore` に**テスト用の read-only なカウンタ／
モード読み出し**（既存の `ui*` atomics と同じ扱い）を足す形が素直。
既存 18 項目と `core/tests/pitch_detector_test.cpp` は不変で PASS すること。
